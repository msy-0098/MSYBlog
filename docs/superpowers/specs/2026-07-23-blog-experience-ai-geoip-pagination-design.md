# 博客体验、AI 能力、IP 查询与分页设计（后端）

- 日期：2026-07-23
- 状态：已确认，待实施
- 配套前端文档：`frontend/docs/superpowers/specs/2026-07-23-blog-experience-ai-geoip-pagination-design.md`
- 交付方式：四阶段开发，每阶段独立验证、提交并推送，全部完成后统一部署

## 1. 背景与目标

后端已具备验证码邮件、AI 会话与 SSE、文章润色、运营分析雏形及部分分页参数，但验证码缺少真实冷却约束，邮件没有品牌资源，AI 运行时与单一实现耦合，部分接口存在伪分页或固定第一页问题，也缺少本地 IP 归属地查询。

本次后端目标：

1. 为验证码发送增加邮箱、用途和 IP 维度的真实限流；
2. 建立安全、一致、可被前端映射的错误响应；
3. 使用 Go Embed 和 CID 发送带 MSY Logo 的多部分邮件；
4. 抽象 OpenAI 兼容 Provider，补齐 AI 健康检查、限制、可靠状态和运营报告；
5. 基于 DB-IP Lite MMDB 提供管理员 IP 查询；
6. 修复伪分页并为长列表提供稳定分页。

## 2. 非目标

本期不包含：

- 面向游客开放 AI 或 IP 查询；
- 复杂多 Provider 管理后台；
- RAG、向量数据库或知识库；
- 远程 IP 查询 API 作为主要数据源；
- 保存 IP 查询历史；
- 将 MMDB 数据文件提交到 Git；
- 改变 Dashboard 固定 Top 列表为分页列表。

## 3. 验证码发送与限流

### 3.1 冷却键与限制

验证码发送至少使用两类限制：

- 邮箱用途键：`normalizedEmail + purpose`，冷却 60 秒；
- 客户端 IP 键：限制短时间高频请求，具体阈值通过配置给出合理默认值。

`purpose` 只接受 `register` 与 `reset`。邮箱须标准化后再构造键。进程内限流应提供清理机制；若项目已有共享缓存设施则优先复用。限流检查在 SMTP 调用前完成。

IP 限流依赖经过可信代理策略解析的客户端 IP，不能盲信任任意来源的 `X-Forwarded-For`。

### 3.2 响应结构

成功：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "sent": true,
    "cooldownSeconds": 60,
    "expiresIn": 600
  }
}
```

冷却中：

```json
{
  "code": 429,
  "message": "验证码发送过于频繁，请稍后再试",
  "data": {
    "retryAfter": 37
  }
}
```

`retryAfter` 取向上取整的剩余秒数，最小为 1。发送失败不得占用完整冷却时间；若为防止 SMTP 故障时被持续轰炸，可设置独立的极短失败退避，但不能伪装成成功冷却。

### 3.3 安全与可观测性

- 日志不记录完整验证码、SMTP 凭据或完整邮箱；
- 对邮箱做脱敏后记录用途、结果和限流原因；
- SMTP 内部错误仅记录服务端日志，对外返回稳定业务提示；
- 注册与重置密码保持一致的防枚举策略，不通过响应泄露邮箱是否存在。

## 4. API 错误契约

所有 API 保持项目现有统一外壳：

```json
{
  "code": 400,
  "message": "提交内容有误",
  "data": null
}
```

规范：

- HTTP 状态与业务 `code` 含义保持一致；
- 参数校验错误可以返回安全、具体的字段级信息；
- SQL、SMTP、Provider、堆栈和内部配置不得直接出现在响应；
- AI Provider 错误映射为稳定的超时、限流、不可用或配置错误；
- 429 在 `data.retryAfter` 返回可选等待秒数；
- 401 与 403 严格区分未认证和无权限；
- IP 查询的输入错误属于普通校验失败，不进入访问攻击计数或自动封禁逻辑。

## 5. MSY 品牌验证码邮件

### 5.1 资源处理

从用户提供的原始 Logo 裁掉多余黑色留白，保留黑底银色横向 MSY 标识，并压缩为邮件专用 PNG。生成的资源放入后端源码资源目录，使用 `//go:embed` 编译进程序。

只提交处理后的邮件资源，不提交临时导出文件或原始聊天缓存路径。

### 5.2 MIME 结构

邮件同时提供纯文本和 HTML，并以内嵌资源承载 Logo：

- 外层 `multipart/related`：HTML 与 CID Logo；
- 正文使用 `multipart/alternative`：纯文本和 HTML 两种版本；
- Logo 具有稳定的 `Content-ID`、正确 MIME 类型和替代文字；
- Subject 使用 UTF-8 编码；
- MIME Boundary 使用安全随机值或标准库生成方式；
- HTML 不依赖脚本、外链 CSS 或外部图片。

模板突出验证码、10 分钟有效期、安全提醒和“非本人操作请忽略”。HTML 与纯文本包含相同关键语义。

### 5.3 测试

使用内存缓冲或假的 SMTP 发送器验证：

- Subject 编码；
- `multipart/related` 与 `multipart/alternative`；
- HTML、纯文本、CID 引用和 PNG 附件；
- 验证码和用途文案；
- SMTP 失败时的安全错误映射。

## 6. AI Provider 与健康检查

### 6.1 接口抽象

保持 OpenAI 兼容协议，运行时不再由 Handler 或 Service 直接绑定 DeepSeek 客户端：

```go
type Provider interface {
    Chat(ctx context.Context, req ChatRequest) (ChatResult, error)
    Stream(ctx context.Context, req ChatRequest, emit func(StreamChunk) error) (Usage, error)
    Health(ctx context.Context) HealthResult
}
```

当前 DeepSeek 作为默认 OpenAI 兼容实现。配置层保留 Provider 类型、Base URL、模型和凭据字段的扩展能力，但本期不建设复杂多供应商管理页面。

### 6.2 状态接口

```http
GET /api/admin/ai/status
POST /api/admin/ai/health-check
```

状态响应仅包含启用状态、Provider、模型、配置完整性、脱敏的 Base URL 摘要和最近健康检查结果。不得返回完整 API Key。

健康检查使用短超时和最小请求，记录状态、耗时、检查时间及安全错误摘要；不得把 Provider 原始响应直接透传给客户端。

### 6.3 限制与并发

- 限制单次用户输入长度和上下文总长度；
- 限制管理员维度的请求频率；
- 限制全局和单管理员并发流数量；
- Provider 超时和上游限流映射为稳定错误；
- 客户端断开或停止生成时取消 Context；
- 记录请求耗时、成功状态和用量，不记录敏感配置；
- 达到长度、频率或并发上限时返回明确业务码，必要时携带 `retryAfter`。

## 7. AI 会话、消息与可靠重试

### 7.1 消息状态

AI 助手消息状态统一为：`streaming`、`completed`、`aborted`、`failed`。

- 创建流时写入 `streaming`；
- 正常结束写入 `completed` 与最终 Token 用量；
- 用户主动停止或连接取消写入 `aborted`；
- Provider、解析或持久化错误写入 `failed`；
- `aborted` 和 `failed` 消息不作为后续完整上下文。

重试应保存 `parent_message_id` 或 `retry_of_id` 等关系，让新尝试基于原用户问题和原上下文生成，不把失败的助手文本当成新用户消息。

### 7.2 分页

- 会话：按 `updated_at DESC, id DESC` 游标分页，默认 20，最大 50；
- 消息：按稳定 `sequence` 反向游标分页，默认 50，最大 100；
- 响应包含 `nextCursor` 和 `hasMore`；
- 游标必须包含排序所需字段并进行安全编码；
- 数据库查询在 SQL 层使用 `WHERE`、`ORDER BY` 和 `LIMIT`，不能先加载全部再切片。

## 8. 文章润色

保留现有润色能力，但接口返回候选正文和必要元信息，不直接覆盖文章。服务端应：

- 校验输入长度与文章权限；
- 使用博客润色专用系统 Prompt；
- 记录状态、耗时和 Token；
- 失败时不修改文章；
- 只有前端明确确认应用后，才通过既有文章更新接口持久化；
- Provider 原始错误仅写日志并安全映射。

## 9. AI 运营报告

### 9.1 数据模型

新增运营报告记录，字段至少包括：

- ID、管理员 ID；
- 时间范围：7、30 或 90 天；
- 请求状态；
- Markdown 报告；
- Provider 与模型；
- 输入、输出和总 Token；
- 耗时；
- 安全错误摘要；
- 创建和更新时间。

每个站点仅保留最近 20 份，新增成功报告后清理更早记录。删除和重新生成必须要求管理员权限。

### 9.2 分析输入

Prompt 使用已有聚合数据：访问趋势、热门文章、站内搜索词、评论统计、异常 IP 摘要和内容表现。不新增访客原始隐私数据，也不把不必要的原始 IP、User-Agent 或个人信息发送给 Provider。

### 9.3 API

提供：

- 生成 7、30、90 天报告；
- 查询最近报告列表；
- 查看单份报告；
- 删除报告；
- 基于原时间范围重新生成。

报告列表默认每页 10，最大 20；即使仅保留 20 份，也保持一致的列表响应结构。

## 10. DB-IP Lite IP 查询

### 10.1 数据源与部署

- 使用本地 DB-IP Lite MMDB；
- 城市库提供国家、省份、城市和经纬度；
- ASN 库提供 ASN 与组织；
- MMDB 文件位于运行时数据目录并加入 `.gitignore`；
- 仓库提供下载或更新脚本及配置示例，不提交数据库文件；
- 服务启动时加载数据库，支持文件缺失时降级并给出可诊断状态；
- 返回数据源名称和数据库构建或更新时间。

### 10.2 API

```http
POST /api/admin/ip-lookup
Content-Type: application/json

{"ip":"8.8.8.8"}
```

接口仅管理员可用。响应包含规范化 IP、地址族、国家、省份、城市、经纬度、ASN、组织、数据源、数据库更新时间以及可选的“未命中”状态。

### 10.3 输入与安全

使用 `net/netip.ParseAddr` 严格解析单个 IP：

- 拒绝 URL、主机名、CIDR 和带端口字符串；
- 拒绝 IPv6 Zone 标识；
- 私网、回环、链路本地、组播、未指定和保留地址返回明确的不可查询原因；
- 不接受自定义 Provider、URL 或文件路径，避免 SSRF 和任意文件读取；
- 查询行为不写历史，不进入自动封禁逻辑。

### 10.4 可信代理

审计现有 `ClientIP()`：

- 仅当直接连接来源属于配置的可信代理网段时读取 `X-Real-IP` 或 `X-Forwarded-For`；
- 否则使用 `RemoteAddr`；
- 多级代理链按可信边界从右向左解析；
- 默认只信任生产 Nginx 所在回环或明确配置网段；
- 日志区分直接来源和解析后的客户端 IP，避免伪造头绕过限流或污染统计。

## 11. 全站分页

### 11.1 游客端

- 评论：`created_at + id` 游标，默认 20，最大 50；
- 归档：`published_at + id` 游标，默认 50，最大 100；
- 首页项目：新增 `limit`，首页传 3，服务端设置合理上限；
- 项目页、友链页和分类入口不做客户端分页，但服务端设置最大返回量；
- 评论和归档必须在数据库层查询，不再一次加载全部数据。

### 11.2 管理端

以下列表采用页码分页，默认 20，最大 100，并返回 `items`、`page`、`pageSize`、`total`：

- 用户；
- 分类；
- 标签；
- 项目；
- 友链；
- IP 封禁记录。

AI 会话和消息使用第 7.2 节的游标分页。Dashboard Top 5、Top 10 和趋势摘要维持固定数量。

### 11.3 兼容策略

优先兼容现有响应字段；若必须调整结构，先增加新字段和前端适配，再移除旧路径。所有分页参数设置下限、默认值和最大值，排序增加唯一 ID 作为第二排序键，避免重复或遗漏。
